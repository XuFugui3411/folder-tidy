identity() 时间包含打开文件、元数据核对和 SHA-256，不是纯 SHA 运算时间。save() 时间包含 JSON 序列化、写入、flush、fsync、替换日志及清理临时日志。各列独立取中位数，不保证分项中位数之和等于总耗时中位数。包装器计数和计时本身也有开销。

## 代码路径核对

成功整理一个文件会进行四次完整哈希：生成 pending 前一次；创建硬链接前核对源文件一次；链接后分别核对目标和源文件各一次。因此 N 个文件的整理阶段逻辑哈希读取量为总内容大小的 4 倍。

整理阶段先保存一次初始日志，然后每个文件分别保存 pending 和 moved，因此有 `2N + 1` 次完整日志写入。日志内容随已处理文件数增长，累计序列化和写入量呈 O(N²) 增长。

正常成功撤销也完整哈希四次 / 文件，并执行 `2N` 次完整日志写入。撤销开始时日志已包含全部 N 个条目，因此也存在 O(N²) 的累计日志写入。逐次计数、逻辑读取量、日志量和耗时均保留在原始 JSON 中。

## 如何据此判断优化

1. 大量小文件：先考虑改造整份日志反复重写。可以评估追加式日志或分段记录，但需要保持“意图落盘后再移动”，并补齐不完整尾记录、pending、撤销中断和重试的恢复测试。不要直接取消 fsync 来换取好看的耗时。
2. 大文件：四次读取可能成为主要成本。先结合本报告的 identity() 耗时判断，再评估基于文件句柄与元数据的核对策略；任何减少哈希的设计，都需要重新验证同路径替换、内容修改和外部并发修改的边界。
3. 比较改动前后时，在同一机器、同一卷、同一组样本上重复运行，比较中位数和波动范围。本次只记录基线，不实施上述算法优化。

## 复现

```powershell
python tools/benchmark.py --workdir D:/folder-tidy-benchmark --output baseline.json --repeats 3
```

工作目录应放在要测的卷上。脚本只创建和清理自己生成的 trial-* 子目录；报告路径由调用者指定。可用 `--case small-100` 等参数只运行一组。所有阶段均调用真实文件操作和 fsync，没有用模拟移动或模拟刷盘代替。

基准会校验每次正常整理的四次哈希 / 文件、`2N+1` 次日志写入，以及撤销的四次哈希 / 文件和 `2N` 次日志写入；还原后核对原文件身份和大小、分类目录已清空。若有失败或计数不符会直接终止，不会把失败混入成功性能统计。
